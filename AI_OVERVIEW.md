## 1. TL;DR — What this is

**Lake Evendim** is an **MSP "data lake" control plane**: a single full-stack Next.js
app that ingests data from MSP tooling (Microsoft 365, PSA, RMM, security, backup,
billing) into one PostgreSQL store, and exposes it through:

- an **admin web UI** (RBAC, SSO, services, org matching, audit log), and
- **API-key-authenticated data endpoints** (`/api/data/*`) that downstream dashboards consume.

Ingestion runs in a **separate background worker** (BullMQ) that executes per-service
**connectors** and writes normalized records back to the DB.

It is **early-stage / pre-refactor** (the latest commit literally says "preparing for
refactoring"). Treat it as a working prototype, not a hardened product.

## 5. Architecture & processes

```
Browser ──auth(creds/SSO)──▶ Next.js (UI + /api) ──▶ PostgreSQL (Prisma)
                                   │   │
                                   │   └──cache──▶ Redis ◀──broker──┐
                                   │                                 │
   downstream apps ──Bearer le_live_…──▶ /api/data/* (API-key authed)│
   external svc ──HMAC──▶ /api/webhooks/{slug} ──enqueue──▶ BullMQ ──┘
                                                                      │
                                            Worker process (npm run worker)
                                            ──▶ Connectors (M365/Halo/Todyl)
                                            ──▶ external APIs ──▶ write to DB
```

**Two processes, by design:**
1. **Web app** (`next dev` / `next start`) — serves UI + API; only *enqueues* sync jobs.
2. **Worker** (`tsx src/worker/sync.ts`) — consumes the `service-sync` queue, runs connectors, writes records + `ServiceSyncLog` + `AuditLog`. Concurrency 3, 3 retries w/ exponential backoff.

## 7. Data model (Prisma → PostgreSQL)

- **Auth/RBAC:** `User`, `Account`, `Session`, `VerificationToken`, `Role`, `Permission`,
  `RolePermission`, `Group`, `UserRole`, `UserGroup`, `GroupRole` (roles AND groups grant permissions).
- **Integrations:** `Service` (status, `syncMode` POLLING/WEBHOOK, encrypted `config`, poll interval), `ServiceSyncLog`.
- **Organizations:** `Organization`, `OrgMapping` (org ↔ external system IDs w/ match confidence), `OrgGroup`, `OrgGroupMember`.
- **Platform:** `SsoConfig`, `ApiKey` (SHA-256 `keyHash`, `keyPrefix`, scopes), `App`, `Setting`, `AuditLog` (indexed).
- **Synced "lake" records** (unique on `[serviceSlug, externalId]`, soft-linked to org):
  `Ticket` (HaloPSA), `SecurityEvent` (Todyl), `CloudUser` (Microsoft 365).

## 9. Auth model (important for AI reasoning)

- **UI users:** Auth.js JWT sessions. Credentials provider (bcrypt + `isActive`) or Microsoft Entra ID.
- **Generic login error is by design:** `authorize()` returns `null` for *any* failure
  (bad password **and** DB unreachable), surfaced as "email or password is incorrect."
  → If login fails, **check the DB is up** before suspecting credentials.
- **Machine/API:** `Authorization: Bearer le_live_<key>` → SHA-256 lookup in `ApiKey.keyHash`,
  status+expiry checks, scope gating via `hasScope()` (`*` = wildcard; session auth = full access).
- **Webhooks:** per-service HMAC-SHA256 (`timingSafeEqual`) using `metadata.webhookSecret`.
- **Seeded dev admin:** `admin@evendim.local` / `Admin1234!` (Super Admin). **Dev-only — rotate before any shared use.**

## 10. How to run (verified working)

```bash
# 1. Backing services on the ports the .env expects (5433 / 6380)
docker run -d --name le-postgres -e POSTGRES_PASSWORD=password \
  -e POSTGRES_DB=lake_evendim -p 5433:5432 postgres:16-alpine
docker run -d --name le-redis -p 6380:6379 redis:7-alpine

# 2. Schema + seed (this project uses db push, NOT migrations)
npm run db:push
npm run db:seed

# 3. Two processes
npx next dev -p 3001     # web UI + API  → http://localhost:3001
npm run worker           # background sync worker (needed for syncs)
```

- **App URL: http://localhost:3001** (NOT 3000 — that's the qct-dev stack).
- The `dev` npm script is bare `next dev` (defaults to 3000); pass `-p 3001` so it matches `AUTH_URL`.
- Health check: `curl -s http://localhost:3001/api/health` → expect `database:"ok"`, `redis:"ok"`.

**Key env vars** (`.env`, all currently set): `DATABASE_URL` (→:5433), `REDIS_URL` (→:6380),
`AUTH_SECRET`, `AUTH_URL` (→:3001), `AUTH_MICROSOFT_ENTRA_ID_{ID,SECRET,TENANT_ID}`,
`ENCRYPTION_KEY` (64-hex; if unset, service creds stored as plaintext JSON — dev only),
`NEXT_PUBLIC_APP_{URL,NAME}`.

## 12. Known gaps / refactoring notes (read before changing things)

1. **`.next/` build output is committed to git** — should be `.gitignore`d; causes constant churn.
2. **No automated polling scheduler** — schema has `pollInterval`/`nextSyncAt`, but nothing
   enqueues syncs on a timer. Syncs are manual or webhook-triggered only.
3. **MFA is scaffolded, not enforced** — `auth.ts` accepts any truthy TOTP code; otplib unused in the auth path.
4. **Default admin creds seeded** — must change before non-local use.
5. **Encryption optional in dev** — without `ENCRYPTION_KEY`, third-party creds persist as plaintext JSON.
6. **8 of 11 services have no connector.**
7. **Auth.js Prisma adapter + JWT strategy** — DB `Session` table is largely vestigial (no easy session revocation).
8. **No tests** despite a `playwright` dependency; **no CI / Dockerfile / compose** in the repo
   (backing services are started ad hoc).
9. **Dev `next dev` script lacks `-p 3001`** — easy to accidentally collide with port 3000.
